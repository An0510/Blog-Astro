## WaitGroup：等你登记过的那些人

`sync.WaitGroup` 用来等一组你 `Add` 过的任务都 `Done`，**不是**等进程里每一个 goroutine。`Wait` 会堵住**当前**这个 goroutine（常常是 `main`）。

```go
var wg sync.WaitGroup
for i := 1; i <= 3; i++ {
	wg.Add(1)
	go func(id int) {
		defer wg.Done()
		fmt.Println("完成", id)
	}(i)
}
wg.Wait()
fmt.Println("全部结束")
```

`defer wg.Done()` 能保证函数提前 `return` 时也会把计数减掉。

把 `i` 当成参数 `id` 传进新的 goroutine，是一种很清楚的写法：每个 worker 拿到的是当时那一轮的值。需要纠正的是——**从 Go 1.22 起**，`for` 每轮迭代都有自己的循环变量，再在闭包里直接读 `i`，也不会再踩到 1.22 之前那种「大家都看到最后一次的 i」的经典坑。把变量当参数传入仍然值得保留，但它是清晰的习惯，不再是「当前 Go 里不这样写就一定会错」。如果你会碰到 1.21 及更早的代码，旧坑才仍然成立。

配合上一篇那个「3 个 worker、只发 1 个任务再 close」的例子，整条流程可以记成：

**`Add` 三次 → 启动并在 `range` 上等待 → 发送 1 个任务（只有 1 人处理）→ `close` → 全部退出 `range` → `Done` 三次 → `Wait` 返回。**

在 `close` 之前，即使有人已经处理完那唯一的任务，只要函数还没返回，`Done` 就还没执行，计数仍是 3。

> [!NOTE]
> **口述 30 秒：** WaitGroup 等一波登记过的任务结束；`Add` / `Done` / `Wait` 要配对。

## Mutex 和 RWMutex

多 goroutine **同时改同一块可变数据**时要加锁。这和「有没有指针」无关——指针反而更容易让多方碰到同一份数据。channel 交接本身带同步，管道里递过去的那一份通常不必再套一把 Mutex；如果同时还在改 channel 之外的共享变量，那边仍要锁。

`sync.Mutex` 是互斥锁：同一时刻只有一个持有者。`sync.RWMutex` 是多读单写，读多写少时更合适。选哪一种取决于访问模式，不是「有锁就用读写锁」。

```go
var mu sync.Mutex
var count int
mu.Lock()
count++
mu.Unlock()
// 没锁时，很多 goroutine 同时 count++，结果常常对不上（读-加-写互相覆盖）
```

口诀仍然有用：**不要通过共享内存通信；要通过通信共享内存（channel）。** 真要共享内存，就加锁。

<details>
<summary>复习问答：锁竞争时会一直自旋吗？</summary>

不会永远自旋。实现上，短时间会先 **spin（自旋）** 试着抢锁；抢不到就会 **park**，睡在等待队列里，把 CPU 让出来。`Unlock` 会唤醒等待者。可以记：先自旋，后休眠，解锁再唤醒。

这是对实现行为的概念记忆，不必展开成源码级细节。

</details>

> [!NOTE]
> **口述 30 秒：** Mutex 互斥；RWMutex 读多写少；竞争时先自旋再 park，Unlock 唤醒。

## sync/atomic

包名是 `sync/atomic`。对**单个**计数器或标志做无锁读写，例如 `AddInt64`、`Load` / `Store`。涉及多个字段的不变量，或更复杂的临界区，用 Mutex。原子操作解决的是「这一下」的可见性和原子性，不是替代所有锁。

```go
var n int64
atomic.AddInt64(&n, 1)
fmt.Println(atomic.LoadInt64(&n))
```

> [!NOTE]
> **口述 30 秒：** 单变量计数用 atomic；复杂状态用 Mutex。

`go test -race` / `go run -race` 可以找数据竞争，属于加分项。知道有这个工具即可，本篇不展开排障流程。

## GMP：概念上看 goroutine 怎么跑

可以用四个角色建立直觉：

- **G（Goroutine）**：用户态的轻量任务，像很多小任务单。栈一开始很小，由 Go runtime 调度，不是一 G 对应一条 OS 线程。
- **P（Processor）**：逻辑处理器，手里有一份本地可运行队列。`GOMAXPROCS` 大致决定 P 的数量。
- **M（Machine）**：真正的 OS 线程。必须绑定一个 P，才能跑 Go 代码；G 跑在「M + P」上。
- **CPU 核**：硬件。M 最终在某个核上执行机器指令。

演示里常见的五个步骤，只用来建立画面，不是调度器的完整规格：

1. 程序里写了很多 `go f()`，运行时创建一批 G，放入各 P 的本地队列；装不下的进 **Global Queue**。此时还没开始跑。
2. 某个 P 从本地队列取出一个 G，放到 Running；对应的 M 绑定这个 P，在某个 CPU 核上执行该 G。
3. 另一对 P / M / 核可以同时跑另一个 G。这就是多路复用：很多 G 落在少量 M 和 CPU 上。浏览器里常见的是单线程事件循环；这里可以是**真并行**，不只靠事件循环交错。
4. 某个 G 阻塞（例如等 channel，或进入一类会卡住的系统调用）时，它会从 Running 卸下。P 和 M 可以立刻从本地队列再取一个 G 继续跑——**协程卡住，不等于整条 OS 线程永远闲置**。
5. 某个 P 的本地队列空了：先看 Global Queue，再 **Work Stealing**（从别的 P 的队列里拿走大约一半）。这样比较不容易出现一核忙死、一核空转。

`go f()` 更接近「丢一张新的任务单 G 进队列」，而不是立刻新开 OS 线程。

> [!NOTE]
> 以上是为了建立直觉的概念模型。实际调度器还有更多状态和边界，本篇不把它写成可以拿去排生产问题的经验。

## 这一篇先记住

- WaitGroup：`Add`、`Done`、`Wait` 配对；只等登记过的任务。
- 共享可变内存才加锁；channel 交接本身已带同步。
- 锁竞争不是永久自旋，会 park。
- 单计数器可以用 atomic；复杂不变量用 Mutex。
- GMP 里，G 很轻，跑在 M + P 上；阻塞的 G 可以被换下去。
